# 首页直达充值与三步兑换界面设计

## 状态与边界

用户已确认布局方向与效果图，并于 2026-09-09 批准继续本地实现。本文件保留已确认的界面规格，具体完成项与实测限制见同日实施计划；未部署、不执行真实充值。

目标用户是使用 CDK 为账号充值的客户。界面应简洁、明确、便于核对账号，沿用现有蓝白工具型风格，不增加营销大标题、渐变背景和装饰动效。

## 一、信息架构

- 首页 `/` 直接呈现单个充值流程，不再先展示服务清单或要求点击“开始充值”。
- 页头保留后台配置的站点品牌、语言切换和明暗切换。
- 主标题为“自助充值”，说明为“输入卡密与账号凭证，核对信息后完成兑换。”
- “批量兑换”“卡密查询”“账单查询”改为轻量次要按钮，分别保留 `/batch`、`/history`、`/billing` 入口，不重做对应业务。
- 原 `/recharge` 入口保持兼容，复用同一充值流程；现有有效查询参数继续传递，不能因入口迁移丢失。
- 去掉原首页四块服务清单及右侧重复流程介绍；单个充值页不再显示四个同等大小的模式标签。

## 二、布局

桌面端标题区约 1120px；主表单居中，最大宽度 840px（按批准效果图落地微调）。三个次要按钮放在标题右侧，表单按用户填写顺序纵向排列。

```text
TaoAi CDK自助充值                              EN  明暗切换
────────────────────────────────────────────────────────
自助充值                     [批量兑换] [卡密查询] [账单查询]
输入卡密与账号凭证，核对信息后完成兑换。

          ① 填写信息 ── ② 确认兑换 ── ③ 查看结果

        ┌────────────────────────────────────┐
        │ CDK 卡密                           │
        │ [输入或粘贴 CDK 卡密              ]│
        │ 校验后显示套餐及卡密状态           │
        │                                    │
        │ 账号凭证       [Session] [邮箱方式]│
        │ ┌────────────────────────────────┐ │
        │ │ 粘贴完整 Session JSON          │ │
        │ │                                │ │
        │ └────────────────────────────────┘ │
        │ 如何获取凭证？            清空凭证 │
        │ 请勿转发或截图分享你的 Session。  │
```

手机端使用单列布局，页边距 16px。三个次要按钮移到主标题下方，可换行但不产生横向滚动。步骤条保留完整名称，主要按钮不被软键盘遮挡。正文与输入字号不低于 16px，次要说明可为 13–14px，交互热区至少 44px。

## 三、三步交互

### 第一步：填写信息

CDK 和凭证同时可见，默认使用 Session；保留当前邮箱与邮箱密码输入方式，不移除已有能力。

主按钮“校验信息，下一步”先检查必填内容，再依次调用原有卡密预览与凭证预检。展示“校验卡密中…”及“核验账号中…”等真实阶段；全部满足现有进入条件后才进入第二步。此按钮绝不调用兑换提交接口。

- 卡密错误显示在 CDK 字段附近，不执行后续凭证预检。
- 卡密预览成功后，在原位显示返回的套餐与状态。
- 凭证错误显示在凭证区域；保留本轮填写内容以便修正。
- 网络错误单独提示，不误标为卡密无效或账号错误。
- 校验期间防止重复触发；如果实现允许修改输入，必须忽略旧输入对应的过期响应。
- CDK 或凭证发生变化后，对应预览、预检与确认摘要失效，重新校验后才能继续。
- “如何获取凭证”解释现有格式要求；不悄悄放宽为当前不支持的纯 Access Token。
- “清空凭证”只清空当前凭证输入及其预检结果，不清空已输入的 CDK。

### 第二步：确认兑换

突出展示目标账号和目标套餐；同时展示当前套餐及订阅状态。到期、续费、付款等原有事实放入可展开的详情区，信息不删除。

保留当前已有的套餐满足限制、欠费提醒及预检未返回摘要时的提示和处理规则；不能把缺失信息显示为“正常”或“已验证”。

操作为“返回修改”和“确认兑换”。只有用户明确点击“确认兑换”才提交。提交期间禁用重复操作。用户返回第一步修改输入后，不沿用上一份确认摘要。

### 第三步：查看结果

保留现有轮询、阶段、时间线、结果账号、卡号尾号及结果说明，界面根据返回状态显示处理中、成功、失败或待核查。

- 处理中、pending、review 或结果不确定，不能显示为成功或引导重复兑换。
- 结果说明继续提示应如何查询进度或联系发码方。
- “再兑一张”沿用已有清理行为：清空上一笔 CDK、Session、邮箱密码、预览、预检及结果状态，停止上一笔轮询，回到第一步。
- 不把界面重置解释为后台任务取消，不修改已有订单幂等或状态机语义。

## 四、视觉规范

- 沿用现有主题变量：浅灰页面底色、白色表单、深色标题、蓝色主按钮；保留暗色主题可读性。
- 一处主要内容面板，避免卡片嵌套；圆角约 6–8px，使用细边框，不增加重阴影。
- 每步只有一个主要按钮；次要入口使用描边或文字按钮，不与充值主操作争夺注意力。
- 字段组内间距约 8px，字段组间距约 24px，表单内边距桌面 28–32px、手机 20px。
- 错误与状态同时使用文字和颜色；保留键盘焦点、可访问标签及状态播报。
- 不展示“绝对安全”“不存储任何凭证”等未经验证的承诺；不新增凭证持久化、埋点或日志。

## 五、实现边界（供后续计划使用）

涉及现有 HomeView、RechargeView、路由入口及单个充值的导航展示。首页壳负责品牌和辅助入口，充值流程只保留一份实现，不能复制两套提交逻辑。

不修改后端 API、数据库、卡密状态、计费、鉴权或订单规则；不改变其他三个页面的业务。不得覆盖工作区已有的主题、品牌、安装状态和凭证清空等未提交改动。

- [ ] 首页无需额外点击即可输入 CDK 和凭证；单个充值只有三个主步骤。
- [ ] 原 `/recharge` 与现有有效参数仍可用，四个功能入口均可到达。
- [ ] 两种凭证方式仍可用；第一步正确处理空输入、无效卡密、错误凭证与网络失败。
- [ ] 第一阶段只有预览和预检，不发生真实兑换；第二阶段需明确确认才提交。
- [ ] 返回修改输入、快速连续点击、旧请求晚返回均不会导致错账号摘要或重复提交。
- [ ] 当前套餐限制、欠费提醒、缺失摘要提示保持原有语义。
- [ ] 处理中及待核查不误报成功；结果轮询继续工作。
- [ ] “再兑一张”不残留上一笔凭证或账号信息。
- [ ] 375px、768px、桌面宽度以及明暗主题、语言切换无截断和横向滚动。
- [ ] 用模拟数据与接口替身验证交互；不使用真实客户凭证，不执行付费充值验收。
